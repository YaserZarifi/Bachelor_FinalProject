# طرح و راهبرد آزمون

## ۱. هدف

سامانهٔ شهریاور سه کلاینت (وب شهروند، وب مدیر، اپ موبایل) دارد که همگی روی یک
بک‌اند Django مشترک کار می‌کنند. هدف این مجموعه آزمون، اثبات چهار ادعای اصلی
پروپوزال است:

| ادعای پروپوزال | چگونه آزموده شد |
|-----------------|------------------|
| شهروند بدون حساب کاربری می‌تواند گزارش ثبت و پیگیری کند | آزمون‌های سرتاسری API + توکن مهمان + WebSocket |
| گزارش «قابل اعتماد» است: عکس، مکان و زمان به هم گره خورده‌اند | آزمون‌های فراداده‌های ثبت، دروازهٔ دقت GPS، اثر انگشت یکپارچگی |
| گزارش در نبود اینترنت گم نمی‌شود (Offline-First) | آزمون‌های صف IndexedDB (وب) و AsyncStorage (موبایل) |
| گزارش به‌صورت خودکار دسته‌بندی و اولویت‌بندی می‌شود | آزمون‌های خط لولهٔ NLP: بحران، طبقه‌بند، احساسات، جایگزین LLM |

## ۲. سطوح آزمون

| سطح | نمونه | تعداد تقریبی |
|-----|-------|--------------|
| **واحد** (Unit) | نرمال‌سازی متن فارسی، محاسبهٔ امتیاز بحران، `canonicalMeta` | ≈ ۴۵۰ |
| **یکپارچگی** (Integration) | ذخیرهٔ گزارش → اجرای سیگنال NLP → به‌روزرسانی پایگاه‌داده | ≈ ۲۵۰ |
| **سرتاسری API** (End-to-end) | `POST /api/reports/` تا دریافت توکن مهمان و اتصال WebSocket | ≈ ۱۲۰ |
| **قرارداد** (Contract) | یکسان بودن ماشین حالت و رنگ‌ها میان بک‌اند و سه کلاینت | ≈ ۶۰ |

## ۳. راهبرد: آزمون رفتار، نه پیاده‌سازی

هر آزمون یک **رفتار قابل مشاهده** را می‌سنجد، نه جزئیات داخلی را. برای نمونه،
آزمون‌های `useGeolocation` بررسی نمی‌کنند که چند بار `setState` صدا زده شده؛
بررسی می‌کنند که «موقعیتی با شعاع خطای ۴۵ کیلومتر هرگز پذیرفته نمی‌شود».
نتیجه این است که بازآرایی (refactor) کد، آزمون‌ها را نمی‌شکند، اما تغییر رفتار
حتماً می‌شکند.

## ۴. اصل مهم: آزمون‌ها باید ایزوله (Hermetic) باشند

هیچ آزمونی نباید به داده یا سرویس بیرونی وابسته باشد یا به آن آسیب بزند.
تدابیر اجراشده:

| خطر | تدبیر |
|-----|-------|
| پاک شدن توکن مهمان گزارش‌های واقعی در Redis | `core/test_runner.py` کلاینت Redis را با بدل درون‌حافظه‌ای جایگزین می‌کند |
| نیاز به Redis برای WebSocket | `settings_test.py` از `InMemoryChannelLayer` استفاده می‌کند |
| نیاز به کارگر Celery | `CELERY_TASK_ALWAYS_EAGER = True` |
| تماس واقعی با Groq یا Expo | کلید API پاک می‌شود و همهٔ تماس‌های شبکه mock می‌شوند |
| آلوده شدن `backend/media/` با عکس‌های آزمون | `MEDIA_ROOT` به پوشهٔ موقت هدایت می‌شود |
| بازنویسی مدل آموزش‌دیدهٔ NLP | آزمون `train_nlp` مسیر pickle را به پوشهٔ موقت می‌برد |
| ناپایداری فیکسچرها به‌خاطر سیگنال همگام NLP | `testkit.no_auto_nlp()` سیگنال را موقتاً جدا می‌کند |

نکتهٔ آخر اهمیت ویژه دارد: سیگنال `post_save` ماژول NLP **همگام** روی هر گزارش
تازه اجرا می‌شود و `nlp_meta`، `is_urgent` و حتی `category` را بازنویسی می‌کند.
اگر فیکسچرها این را خاموش نمی‌کردند، صرفِ وجود واژهٔ «خطر» در متن آزمون،
نتیجهٔ آزمون‌های نامرتبط را تغییر می‌داد. در مقابل، آزمون‌هایی که موضوعشان
*خودِ* این سیگنال است، آن را فعال نگه می‌دارند.

## ۵. آنچه آزمون خودکار نشد و چرا

| مورد | دلیل | جایگزین |
|------|------|---------|
| کامپوننت‌های نمایشی React/RN | ارزش آزمون خودکارِ چیدمان بصری پایین و هزینهٔ نگه‌داری آن بالاست | [چک‌لیست آزمون دستی](07-manual-tests.md) |
| دوربین درون‌برنامه‌ای (`getUserMedia` / `expo-camera`) | نیازمند سخت‌افزار و مجوز واقعی مرورگر/دستگاه | آزمون دستی روی دستگاه |
| نقشهٔ Leaflet | رندر نقشه به بوم (canvas) و کاشی‌های شبکه‌ای وابسته است | آزمون دستی + آزمون واحد `toLatLng` |
| ارسال واقعی اعلان Expo | تماس با سرویس بیرونی | mock کامل + آزمون دستی روی دستگاه |
| کارایی و بار (Load) | خارج از دامنهٔ این فاز | پیشنهاد کار آینده |

## ۶. معیار پذیرش

* **همهٔ** آزمون‌ها سبز باشند.
* پوشش کد لایهٔ منطق در هر مجموعه دست‌کم ۹۰٪ باشد. (نتیجه: ۹۴٪ تا ۹۸٪)
* هیچ آزمونی ناپایدار (flaky) نباشد — هر مجموعه سه بار پیاپی اجرا و تأیید شد.
* نقص‌های کشف‌شده که هنوز رفع نشده‌اند، به‌صورت آزمونِ صریحِ «نقص شناخته‌شده»
  ثبت شوند تا پنهان نمانند (بخش [یافته‌ها](05-findings.md)).
