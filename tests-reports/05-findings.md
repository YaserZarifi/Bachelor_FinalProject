# یافته‌ها و نقص‌های کشف‌شده

مجموعهٔ آزمون فقط رفتار موجود را تأیید نکرد؛ **پنج نقص واقعی** و چند نکتهٔ
طراحی را نیز آشکار ساخت. هیچ‌کدام در این فاز «رفع» نشد — چون خواستهٔ اصلی
نوشتن آزمون بود، نه تغییر رفتار محصول — اما هر مورد به‌صورت یک **آزمون صریحِ
«نقص شناخته‌شده»** ثبت شده تا در آینده پنهان نماند و به‌محض رفع، آزمون آن با
صدای بلند بشکند.

---

## ۱. از دست رفتن گزارش در صف آفلاین وب

| | |
|---|---|
| **شدت** | 🔴 بالا — از دست رفتن دادهٔ شهروند |
| **محل** | `frontend-citizen/src/api/offline.js` تابع `saveReportOffline` |
| **آزمون** | `src/api/offline.test.js` › `known issues` › «دو عکس در یک میلی‌ثانیه یکدیگر را بازنویسی می‌کنند» |

### شرح

کلید ذخیره‌سازی در IndexedDB چنین ساخته می‌شود:

```js
id: `${Date.now()}-${Math.round(performance.now())}`
```

هر دو جزء، **دقت میلی‌ثانیه** دارند. اگر شهروند دو عکس را در فاصلهٔ کمتر از یک
میلی‌ثانیه ثبت کند (که در حلقهٔ ثبتِ پیاپی کاملاً ممکن است)، هر دو کلید یکسان
می‌گیرند و `objectStore.put()` بی‌سروصدا اولی را با دومی جایگزین می‌کند.
گزارش نخست **پیش از آنکه هرگز ارسال شود** از بین می‌رود.

این نقص ابتدا به‌صورت یک آزمون **ناپایدار** بروز کرد: آزمون «دو گزارش مستقل
در صف» گاهی موفق و گاهی ناموفق می‌شد. بررسی نشان داد علت، ناپایداری آزمون
نیست، بلکه رفتار خودِ برنامه است.

### راه‌حل پیشنهادی

```js
id: crypto.randomUUID(),
```

پس از این تغییر، آزمون «نقص شناخته‌شده» شکست خواهد خورد و باید معکوس شود
(انتظار: هر دو گزارش در صف باقی می‌مانند).

## ۲. خروجی هندسه GeoJSON نیست (رشتهٔ EWKT برمی‌گردد)

| | |
|---|---|
| **شدت** | 🟠 متوسط — نقشهٔ دو کلاینت از سه کلاینت مختصات نمی‌گیرد |
| **محل** | `backend/core/settings.py` → `INSTALLED_APPS` |
| **آزمون** | `reports/tests/test_serializers.py` › `GeometryEncodingDeviationTests` (۴ آزمون) و آزمون‌های متناظر در `frontend-citizen` و `mobile` |

### شرح

بستهٔ `django-rest-framework-gis` نگاشت «فیلد هندسی GeoDjango → `GeometryField`»
را از داخل `AppConfig.ready()` خود نصب می‌کند. اما `rest_framework_gis` در
`INSTALLED_APPS` **ثبت نشده**، بنابراین این قلاب هرگز اجرا نمی‌شود و DRF برای
`Report.location` به `ModelField` عمومی برمی‌گردد. نتیجه:

```jsonc
// آنچه مستندات و CLAUDE.md وعده می‌دهند:
"geometry": { "type": "Point", "coordinates": [51.389, 35.6892] }

// آنچه سرور واقعاً می‌فرستد:
"geometry": "SRID=4326;POINT (51.389 35.6892)"
```

### اثر روی هر کلاینت

| کلاینت | وضعیت |
|--------|-------|
| **وب مدیر** | ✅ سالم — تابع `toLatLng()` هر دو قالب را می‌فهمد |
| **وب شهروند** | ❌ `flattenFeature` مستقیم `geometry.coordinates` را می‌خواند → `lat`/`lng` برابر `undefined` |
| **موبایل** | ❌ همان مشکل |

### راه‌حل پیشنهادی

یک خط در `core/settings.py`:

```python
INSTALLED_APPS = [
    ...
    'rest_framework_gis',
]
```

پس از این تغییر، چهار آزمون `GeometryEncodingDeviationTests` و دو آزمون
کلاینتی عمداً می‌شکنند و باید به قالب صحیح GeoJSON به‌روزرسانی شوند. تابع
`toLatLng` در داشبورد مدیر همچنان کار می‌کند (هر دو قالب را پشتیبانی می‌کند).

## ۳. پارامتر `dist` در فیلتر مکانی بر حسب **درجه** است، نه متر

| | |
|---|---|
| **شدت** | 🟡 پایین — رفتار غیرمنتظره در «گزارش‌های نزدیک من» |
| **محل** | `backend/civic_api/viewsets.py` کلاس `ReportViewSet` |
| **آزمون** | `civic_api/tests/test_reports_api.py` › `DistanceFilterTests` (۶ آزمون) |

### شرح

`DistanceToPointFilter` تنها زمانی `dist` را متر تفسیر می‌کند که ویوست صفت
`distance_filter_convert_meters = True` را تعریف کرده باشد. `ReportViewSet`
این صفت را ندارد، پس مقدار بر حسب **درجهٔ جغرافیایی** تفسیر می‌شود.

در نتیجه درخواستی که به‌نظر «شعاع ۱۰۰۰ متر» می‌آید:

```
GET /api/reports/?point=51.389,35.6892&dist=1000
```

در عمل شعاعی حدود **۱۱۱٬۰۰۰ کیلومتر** یعنی کل کرهٔ زمین را پوشش می‌دهد.

### راه‌حل پیشنهادی

```python
class ReportViewSet(viewsets.ModelViewSet):
    distance_filter_field = "location"
    distance_filter_convert_meters = True   # ← افزوده شود
```

سپس آزمون `test_the_dist_parameter_is_in_degrees_not_metres` باید به واحد متر
به‌روزرسانی شود.

## ۴. کارمند به کانال زندهٔ گزارش دسترسی ندارد

| | |
|---|---|
| **شدت** | 🟡 پایین — ناهماهنگی میان لایهٔ REST و لایهٔ WebSocket |
| **محل** | `backend/civic_api/consumers.py` |
| **آزمون** | `civic_api/tests/test_websocket.py` › `test_staff_have_no_implicit_socket_access` |

### شرح

در لایهٔ REST، `is_staff` به همهٔ گزارش‌ها دسترسی دارد
(`ReportViewSet.get_queryset`). اما `ReportConsumer` فقط دو شرط را بررسی
می‌کند: «کاربر، مالک گزارش است» یا «توکن مهمان معتبر است». پرچم `is_staff`
اصلاً بررسی نمی‌شود، بنابراین اتصال WebSocket یک کارمند با کد `4403` رد می‌شود.

اثر عملی: داشبورد مدیر نمی‌تواند از همان کانال زندهٔ گزارش استفاده کند و برای
دیدن تغییرات باید صفحه را تازه کند.

### راه‌حل پیشنهادی

در `ReportConsumer.connect` پس از اعتبارسنجی JWT:

```python
if validated.get("is_staff"):
    allowed = True
```

(ادعای `is_staff` هم‌اکنون در توکن دسترسی وجود دارد — آزمون
`test_access_token_embeds_the_staff_flag` آن را تأیید می‌کند.)

## ۵. نقطهٔ پایانی «تحلیل مجدد» فاقد محدودیت مدیر است

| | |
|---|---|
| **شدت** | 🟡 پایین — مصرف منابع توسط کاربر عادی |
| **محل** | `backend/nlp/views.py` کلاس `ReAnalyzeReportView` |
| **آزمون** | `nlp/tests/test_pipeline_integration.py` › `test_a_plain_citizen_can_currently_trigger_re_analysis` |

### شرح

مستند خودِ کلاس می‌گوید «فقط برای ادمین/مدیر»، اما هیچ
`permission_classes` تعریف نشده، پس پیش‌فرض پروژه یعنی `IsAuthenticated`
اعمال می‌شود. هر شهروند وارد‌شده می‌تواند تحلیل مجدد هر گزارشی (حتی گزارشی که
مال او نیست) را فعال کند — که در صورت فعال بودن جایگزین Groq، هزینهٔ API هم
دارد.

### راه‌حل پیشنهادی

```python
from rest_framework.permissions import IsAdminUser

class ReAnalyzeReportView(APIView):
    permission_classes = [IsAdminUser]
```

## نکات طراحی (نقص نیستند، اما دانستن‌شان لازم است)

### الف) امتیاز احساسات، «قطبیت» را می‌سنجد نه «شدت» را

`sentiment_score` برابر است با `(pos − neg) / (pos + neg)`. بنابراین هر متنی که
فقط بار منفی داشته باشد — از «یک اشکال کوچک دارد» تا «افتضاح و وحشتناک است» —
دقیقاً امتیاز `−۱٫۰` می‌گیرد. آنچه شدت را نشان می‌دهد، فیلد `intensity` است.
هنگام تفسیر نمودار «حال‌وهوای شهروندان» در داشبورد باید به این نکته توجه شود.

> آزمون: `nlp/tests/test_sentiment.py` › `test_the_score_measures_polarity_not_magnitude`

### ب) طبقه‌بند محلی روی حدود ۴۰٪ از عبارت‌های واقعی به مدل زبانی ارجاع می‌دهد

اندازه‌گیری روی جملات واقعی و خارج از دادهٔ آموزشی نشان داد ضریب اطمینان مدل
بین ۰٫۱۹ تا ۰٫۵۵ در نوسان است، در حالی که آستانهٔ ارجاع به Groq برابر ۰٫۴۰
است. برچسبِ **بیشترین امتیاز** در همهٔ نمونه‌های آزموده‌شده درست بود (دقت
۱۰۰٪ در انتخاب برچسب برتر)، اما در حدود ۴۰٪ موارد اطمینان کافی برای تصمیم
مستقل وجود نداشت و خط لوله به مدل زبانی ارجاع داد.

این عدد برای پایان‌نامه اهمیت دارد: نشان می‌دهد **جایگزین LLM یک تزئین نیست،
بلکه بخش فعال معماری است** — به‌ویژه برای گزارش‌های کوتاه («چاله در خیابان»)
که n-gram کاراکتری سیگنال کافی از آن‌ها استخراج نمی‌کند.

> آزمون‌ها: `nlp/tests/test_classifier.py` › `PredictionQualityTests`

### ج) دو نسخهٔ متفاوت از منطق NLP به‌طور هم‌زمان وجود دارد

* `nlp/signals.py` — همگام، روی `post_save`؛ `category` گزارش را نیز
  **تغییر می‌دهد**.
* `nlp/tasks.py` — ناهمگام، روی Celery؛ فقط `nlp_suggested_category` را پر
  می‌کند و `category` را دست نمی‌زند.

هر دو آزموده شده‌اند، اما در حال حاضر فقط سیگنال همگام در جریان واقعی ثبت
گزارش اجرا می‌شود. این یعنی تحلیل NLP روی **نخِ درخواست** انجام می‌شود و زمان
پاسخ `POST /api/reports/` را افزایش می‌دهد. اگر هدف معماری، اجرای ناهمگام
است (چنان‌که در `CLAUDE.md` توضیح داده شده)، باید سیگنال حذف و `perform_create`
به صف Celery متصل شود.

> آزمون‌ها: `nlp/tests/test_pipeline_integration.py` › `AutoAnalysisSignalTests`
> و `CeleryTaskTests`
